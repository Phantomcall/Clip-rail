# Audit: Vault v1 (PR #14, branch `isaac/vault-v1`, commit 0f2e50c)

**Scope:** every source change in PR #14: `CampaignVault.sol` (release, flag/resolve/autoResolve, close/closeTo,
sweep, keeper lists), `CampaignVaultLens.sol` (new), `CreatorReputation.sol` (I-2.4), and their interfaces. The
v0 code they interact with (report processing, accrual, register, pause) was re-read where the new code depends on it.

**Spec checked against:** `Cliprail-PRD.pdf` (§5.1–5.4, F5–F8) and `Cliprail-Task-Playbook.pdf` (I-2.1 to I-2.5,
I-3.4, I-3.5), plus the requirements R-1 to R-6 from the vault-core audit (`2026-10-05-vault-core.md` §4).

**Method:** a line-by-line review of the diff; a check of every task's "done when" against the tests; PoC tests for
each suspected issue (`contracts/test/AuditV1Probe.t.sol`, not committed); and the existing suite (93 tests, 10
invariants at 500 × 100 under the CI profile).

## 3. Findings

### V1-1 (Medium): Matured but unreleased earnings can still be clawed back
**What:** `flag` accepts any clip with *unreleased* tranches, and `reject` returns all of them, including tranches
whose hold has already ended but that the keeper hasn't paid yet. The keeper runs every 5 minutes, so every matured
tranche is exposed for up to 5 minutes. If the keeper is down, it stays exposed until someone calls `release`.

**Why it matters:** the hold window is the brand's dispute period. PRD F5 says matured earnings arrive "without the
clipper doing anything", and §1.1 names "rejections after their views have already come in" as the problem
Cliprail solves. As written, the brand's power lasts until the keeper's next run, not until maturity.

**PoC:** `test_probeA_maturedButUnreleasedClawback`. Warp past the hold, flag, reject: the clipper gets 0 and the
$5 returns to the budget.

**Fix (fits, vault 24,401 B):** `flag` first calls `_release(clipId)`, which pays everything already matured, and
only then freezes. Whatever is still unreleased was in hold at flag time. `flag` becomes `nonReentrant`.
Edge cases to document: if the payout address is blacklisted, the matured part can't be paid and stays frozen. The
200-tranche cap per release also applies.

### V1-2 (Medium): `resolve` isn't bounded by the flag deadline
**What:** `resolve` only checks that the clip is Flagged and the caller is the brand. After `flagDeadline`, the
brand can still reject if nobody has called `autoResolve` yet.

**Why it matters:** PRD F6 says "an unresolved flag is accepted automatically after its deadline". With a dead or
slow keeper, the brand gets an open-ended window. The clipper can protect themselves by calling `autoResolve`, but
F5 and F6 say they shouldn't have to.

**PoC:** `test_probeB_resolveAfterDeadline`. The brand rejects 3 days after the deadline.

**Fix (fits):** `resolve` reverts with a new `FlagExpired` error once `block.timestamp >= flagDeadline`. After
that, only `autoResolve` (accept) is possible.

### V1-3 (Medium, design): One reject removes tier 1 permanently
**What:** tier 1 requires `rejections == 0` (PRD §5.4). A reject costs the brand nothing; it actually gets the
unreleased money back. Any brand can flag and reject one tiny clip and drop a clipper to tier 0 until they reach
50k paid views with a reject rate under 5%.

**PoC:** `test_probeD_rejectKillsTier1`. A tier 1 clipper is rejected on a $0.10 clip and drops to tier 0.

**Options (team decision; the code matches the PRD today):**
(a) tier 1 allows a small reject rate, like tier 2;
(b) count at most one rejection per brand per clipper;
(c) keep the rule and rely on brands' public reject rates (R-4).
**Chosen: (b)** (see §6). **Correction to the first version of this report:** (b) stops one brand from
inflating a clipper's reject *rate* (tier 2) by rejecting many clips. It does **not** protect tier 1, because tier 1
still requires zero rejections, so one reject from any brand still removes it.

### V1-4 (Low, design): Self-funded tier raising
A clipper can create a campaign as the brand, clip into it, and get their own budget back as "earnings". The
views must still be real YouTube views that pass the like floor, so the cost is getting the views, not the money.
The `brands` count in stats shows this (1 brand). The UI or campaigns could require `brands ≥ 2` for higher tiers.
**Recommendation:** document it; revisit after the hackathon.

### V1-5 (Info): Interface differs from the PRD; announce before the ABI freeze
PRD §5.1 lists `claimCode` as a vault view, the playbook's keeper (I-3.4) reads `releasableClips` and
`expiredFlags`, and PRD §5.4 has `recordPaid` without `clipId`. In this PR they're on `CampaignVaultLens`
(`recordPaid` gains `clipId`). Nothing in the repo calls them on chain today: web and the oracle use the
TypeScript `claimCode`, and the keeper isn't written yet. David and Patrick should hear about this before I-3.5's
ABI freeze (H6).

### V1-6 (Info): Reject gas is linear in unreleased tranches
`_reject` walks every unreleased tranche: about 2,590 gas each. Measured: 2,016 tranches (7-day hold, 5-minute
reports) cost 5.2M gas. With the keeper running, the number of unreleased tranches is bounded by hold / report
interval. Only if nobody releases a clip for weeks could a reject run out of gas; the flag would then auto-accept,
which fails toward the clipper. `release` is already capped at 200 tranches per call.

### V1-7 (Info): A failing payout is retried forever
A clip whose payout address can't receive the token stays on the pay list, and `releasableClips` returns it on
every run (`ReleaseFailed` each time) until the clipper sets a new payout address. Nothing is lost, but the
keeper (I-3.4) should skip clips with a recent `ReleaseFailed`.

### V1-8 (Info): A flag is one-shot
After a flag is accepted, the brand can never flag that clip again (R-3). A brand should wait until it's sure.
Document this in the brand UI.

### V1-9 (Info): Contract-size headroom
The vault has 223 bytes of headroom (175 with the V1-1 and V1-2 fixes). Any further vault feature must first move
something else to the lens.

|---|---|---|

## 6. Fixes applied (after the first version of this report)

### V1-1: flag pays matured earnings first
- `flag` reverts with `NotFlaggable` unless the newest tranche is still in hold. Unlock times only increase, so
  that's exactly "something is still in hold".
- `flag` writes all flag state first, then pays every tranche whose hold has ended (`_pay`, split out of
  `_release`). External calls come last.
- `flag` is now `nonReentrant`. A failed `flag` reverts the whole call, so the brand keeps its one flag.
- **Found during the fix:** the first version of the fix released before writing state. Slither flagged that
  (`reentrancy-no-eth`, not exploitable with allowlisted tokens). The restructure also closed an edge case: a clip
  with only matured earnings and a blacklisted payout address could still be flagged.
- **Remaining edge (documented):** if a clip has earnings in hold *and* its payout address can't receive the token,
  the matured part can't be paid at flag time and is frozen (and, on reject, returned) with the rest. The clipper
  avoids this by keeping a working payout address.
- **Tests:** `Flag_PaysMaturedTranchesFirst`, `Flag_NothingInHoldReverts`, `Flag_BlacklistedPayout`.

### V1-2: resolve only inside the window
- `resolve` reverts with the new `FlagExpired` error once `block.timestamp >= flagDeadline`. After that, only
  `autoResolve` (accept) works.
- **Test:** `Resolve_RevertsAfterDeadline` (the last second inside the window works; the deadline itself
  doesn't, for both reject and accept).

### V1-3 (b): one rejection per brand
- `recordRejection(clipper, brand)` counts once per (clipper, brand) pair (`rejectedBy`). Repeat rejects by the same
  brand emit no `ReputationUpdated`, but each one is still public as a `Resolved` event.
- `stats.rejections` now means "distinct brands that rejected this clipper".
- **Test:** `Rejections_CountOncePerBrand`.
- **Still open:** tier 1's "0 rejections" rule (PRD §5.4) means one reject from any brand still removes tier 1.
  Options: tier 1 tolerates one rejecting brand, or uses a rate like tier 2. This needs a team decision.

### Invariant handler
- The new rules made random flags and resolves almost always revert: only 2 flags and 0 brand rejects in a
  4,000-call coverage probe.
- The handler now flags clips from the pay list and resolves clips from the flag list. The same probe now reaches
  8 flags, 2 brand rejects and 6 accepts.

- Vault: 24,462 bytes (114 under EIP-170).
- 98 tests pass, including 5 new regression tests.
